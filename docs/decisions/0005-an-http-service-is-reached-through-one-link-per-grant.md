# An HTTP Service is reached through one Link per Grant, behind the same Sessions as a Child

## Context

[ADR-0002](0002-each-grant-shares-one-child-identity-enters-through-the-environment.md) settles Services that Modgud runs as processes and leaves HTTP Services as a future extension. Norn's next build serves MCP itself: `norn serve` binds a loopback address, answers MCP at `/mcp` over Streamable HTTP, and requires `Authorization: Bearer <secret>` with a secret from its token file, `<config_dir>/tokens.toml`, whose `[tokens.<label>]` tables each hold a `secret`. It re-reads that file on every request. It speaks 2025-11-25 through `initialize` and 2026-07-28 statelessly, issues no `Mcp-Session-Id`, answers GET and DELETE with 405, sends one `application/json` answer per POST, sends no server-initiated messages, and refuses any request that carries an `Origin` header. It needs no caller Identity. Norn's `/mcp` was not yet built when this decision was written, so these behaviors are Norn's stated contract, not observed ones.

Everything Modgud does for Callers lives in its Sessions: binding to a Grant, eviction, request limits, renumbering, stream bounds, and, from Phase 2, Selector enforcement. Callers such as claude.ai and ChatGPT still expect a 2025-era Session.

## Decision

### HTTP Services and Links

- **A Service is a process Service or an HTTP Service.** A process Service is configured with `command`, and Modgud runs it as a Child under ADR-0002. An HTTP Service is configured with `url` instead, and Modgud reaches it over Streamable HTTP. A Service names exactly one of the two, and a Service that names both, or neither, is a configuration error.
- **One Link per Grant, in the Child's place.** For an HTTP Service, each Grant has one Link: the `initialize` result and tool list Modgud holds for that Grant, and the Grant's requests in flight on the Service. A Link owns no process. One Link never serves two Grants. Every rule ADR-0002 states for a Grant's Child, under Sessions and Messages, applies to a Grant's Link unless this decision says otherwise. That covers Session binding, the Session and request limits, eviction, renumbering of request ids and progress tokens, the requests Modgud answers itself, generic errors, unresumable and bounded streams, and a Session outliving what serves it. So do [ADR-0001](0001-callers-reach-services-through-grants-modgud-is-its-own-oauth-server.md)'s Selectors and visible tool list.
- **Modgud is the Service's only client in the Link.** Modgud builds every request to the Service itself and forwards nothing from a Caller's HTTP request: no header, cookie, or query. It sends `Authorization: Bearer <secret>`, `Content-Type: application/json`, `Accept: application/json, text/event-stream`, `Accept-Encoding: identity`, after `initialize` an `MCP-Protocol-Version` that names the version the Service's `initialize` result gave and never a value taken from a message, and the Service's `Mcp-Session-Id` when it issued one. Beyond these it sends only what HTTP and Bun's `fetch` add themselves: `Host`, `Content-Length`, `Connection`, and a `User-Agent` that names Modgud. It sends no `Origin` header. It never follows a redirect. It connects to the URL's address directly and never through a proxy, whatever proxy variables Modgud's environment sets, because Bun's `fetch` otherwise honors `HTTP_PROXY` and would hand the bearer to the proxy.

### Configuration

- **`url` is a loopback `http` URL.** It uses the `http` scheme, its host is the loopback address `127.0.0.1` or `[::1]`, written in any form the URL parser normalizes to one of them, and it has no user information, query, or fragment. Its path, `/` included, is the Service's MCP endpoint, such as `http://127.0.0.1:28472/mcp`. Modgud refuses any other URL, including one that names a host such as `localhost`: Bun resolves `localhost` to `::1` before `127.0.0.1`, so a name could reach an address the Service does not bind. Plain HTTP carries the bearer, so it never leaves the host, and the Service runs on Modgud's host as ADR-0001 requires.
- **The bearer comes from a file.** `bearer_file` names the file, as an absolute path or one starting with `~/`, which expands to home as `store.path` does. Without `bearer_key`, the secret is the file's contents with surrounding whitespace removed. With `bearer_key`, a dotted path such as `tokens.default.secret`, Modgud parses the file as TOML and takes the string at that path; each dot separates two keys, so the path cannot name a key that contains a dot. The secret must be non-empty and hold only visible ASCII characters. Norn's own token file therefore works unchanged, with `bearer_key = "tokens.<label>.secret"`, and so does any server whose secret sits alone in a file.
- **Modgud reads the bearer when a Link starts.** It does not read it at startup, so Modgud starts even when the Service has not yet created its token file. A missing or unreadable file, a file that is not valid TOML when `bearer_key` is set, a path that names no string, or an invalid secret makes that start fail. Modgud logs a warning that names the Service, the file, and which of these happened, never the parser's message, which can quote the file's contents. Modgud never logs the secret.
- **`tool_list_max_age_seconds`** sets how old the stored tool list may be when a `tools/call` is checked against it: 60 by default, from 1 to 3600.
- **`idle_timeout_minutes` keeps its meaning,** with the same default and range as for a process Service. An HTTP Service takes none of `args`, `command`, `cwd`, `env`, or `identity_env`.

### The Link's life

- **A Link starts on demand.** Modgud starts a Grant's Link when the Grant has no Link running and a Caller's `initialize` needs the Link's result or a request must be forwarded, as ADR-0002 starts a Child. A failed start fails what waits for it as ADR-0002 says: an `initialize` gets HTTP 502, and a request on an open Session a JSON-RPC error response. To start it, Modgud reads the bearer, POSTs one `initialize` request that asks for protocol version `2025-11-25`, with client information naming Modgud and no client capabilities, then POSTs `notifications/initialized`. Once Selectors are enforced in Phase 2, it then fetches every page of `tools/list`, as ADR-0001 requires. These start requests are sent, answered, and bounded like every other request below, and share one 30-second deadline. A start fails when it misses the deadline, when the bearer cannot be read, when any start request gets a bad answer or an answer that stops a Link, or when the Service answers `initialize` with an error or with a protocol version that is not a 2025-era version Modgud supports. A failed start counts as a failure under ADR-0002's backoff. A start that succeeds keeps the result, which replaces the result an earlier Link gave, and ADR-0002's check of each Session against a changed result applies.
- **Modgud speaks the 2025-era protocol to every HTTP Service.** It asks for `2025-11-25`, never probes 2026-07-28, and never sends `server/discover`. Whether Modgud speaks 2026-07-28 to a Service that supports it is settled with the design for 2026-07-28 Callers (ADR-0002, MCP revision 2026-07-28), for Children and Links alike.
- **A Service's `Mcp-Session-Id` binds the Link.** When the Service answers `initialize` with an `Mcp-Session-Id`, Modgud sends it on every later request of that Link and on no other Link. When a Link with a session id stops, other than for a 401 or a 404 on that id, Modgud sends the Service one DELETE with that id and the bearer the Link started with. Its answer, whatever it is, is ignored and stops nothing.
- **Each request is one POST.** Modgud sends each request, its own or a Caller's, in its own POST and reads the answer, whether the Service sends one `application/json` message or a `text/event-stream`. On a stream, each event's data is one JSON-RPC message; events with empty data, comments, and `id` and `retry` fields are ignored. The response and every progress notification reach their request as they would from a Child, and Modgud stops reading once the response has arrived. Modgud never resumes a stream, so a Service that ends a stream before its response, expecting the client to resume it with a GET, fails that request. A notification or a response Modgud sends, such as its answer to a Service's `ping`, goes in its own POST, and Modgud expects 202 with no body.
- **Modgud's own notifications, responses, and DELETEs are bounded.** Apart from the start's requests, which the start's deadline bounds, each has 2 seconds, and a Link holds at most 64 of them in flight. One more is dropped and logged, which is safe because each is advisory: a cancellation, an answer to a request a conforming Service never sends, or the end of a session. Shutdown waits no longer than 2 seconds for them.
- **A message is at most 10 MiB,** the same bound as a Child's message, counted after any decoding. An event counts toward the bound as Modgud reads it, whether or not it has ended. A larger message is a bad answer to its request.
- **Messages the Service sends outside a response follow ADR-0002.** `notifications/tools/list_changed` and the other list-change notifications go to every Session of the Grant, and a tool list change makes Modgud fetch the tool list again. A logging notification goes to Modgud's log. A request from the Service gets ADR-0002's answer, POSTed back to the Service. Modgud opens no GET stream on the Service, so it sees only the messages the Service sends on a POST's stream.
- **The stored tool list has a maximum age.** Once Selectors are enforced, Modgud checks a Caller's `tools/call` against the stored tool list only when that list was fetched no more than `tool_list_max_age_seconds` earlier. Otherwise the call waits while Modgud fetches every page of `tools/list` again, and calls that arrive meanwhile wait for the same fetch. The fetch has 30 seconds. A fetch that misses that deadline or gets a bad answer fails the calls that wait for it, and the stored list stays as it was. A Child needs no such rule, because its tool list changes only with the notification ADR-0001 requires or with a new process, while an HTTP Service can be upgraded behind a running Link without either.
- **Cancelling a request aborts its POST.** For a Caller's `notifications/cancelled`, or a request of a Session that ends, Modgud POSTs the renumbered `notifications/cancelled` to the Service and then aborts that request's POST. A Service without a session id cannot match a cancellation sent in another POST to its request, so for such a Service, Norn included, the abort is the cancellation. Because the Service may keep working on a cancelled request, it keeps counting against the Grant's request limit for 60 seconds after it was cancelled, as ADR-0002 counts a cancelled request on a Child.
- **A Link stops when idle.** The idle clock starts once the Link has started. A Link stops once its Service's idle timeout passes with no message in either direction between Modgud and the Service. A request in flight does not hold it open, as for a Child.
- **A Link stops when the Service cannot be reached or refuses Modgud.** These answers show that the Link, not one request, is broken: the Service refuses the TCP connection, answers any request or notification with 401, or answers with 404 a request or notification that carries the Service's session id. A DELETE's answer never counts. Each stops the Link. A refused connection or a 401 counts as a failure under ADR-0002's backoff. A 404 on the session id does not, because the transport tells a client to start a new session then: the next request or `initialize` starts a new Link, whose `initialize` carries no session id, and a start that fails then counts as a failure. The next start reads the bearer again, so a rotated token takes effect after one 401.
- **Any other bad answer fails only its request.** A status other than 200 for a request or 202 for a notification or response, a redirect, a reset or closed connection, a body that is neither one JSON-RPC message nor an event stream, a response whose id is not the request's, a stream that ends before its response, or a message over 10 MiB gives that request Modgud's generic error response and leaves the Link running. Bun reports a reset, a close before the answer, and a reused keep-alive connection that the Service had already closed alike, so none of them stops the Link. A bad answer to a notification, other than one that stops the Link, is logged and dropped.
- **Stopping a Link cancels its work.** When a Link stops, every Caller request in flight on it gets a JSON-RPC error response at once, and the Grant's Sessions stay open, as when a Child exits. Each of those requests is cancelled as above, except that Modgud sends no `notifications/cancelled` when the Link stopped because the Service refused the connection, answered 401, or answered 404 on its session id, and only aborts the POST. Answers to a stopped Link's POSTs, its cancellations and its DELETE, never stop a Link and never count toward backoff. A new Link may start at once; nothing waits for an exit. Unlike a stopped Child's work, a stopped Link's work may still finish on the Service. A Grant's end stops the Link as ADR-0002 stops a Child. On shutdown, Modgud sends each cancellation and then aborts every POST without waiting.

### Identity

- **An HTTP Service receives no Identity in v1.** The Service configuration has no Identity field for it, and in Phase 2 Modgud refuses to create or change a Grant that carries an Identity for an HTTP Service. How an Identity would reach an HTTP Service is settled once a Service needs one, because the receiving side is not yet designed.

## Considered options

- Pass a Caller's request through to the Service with its bearer swapped, and let 2026-07-28 Callers through untranslated. Rejected: Modgud would still need its own Sessions for 2025-era Callers and would still parse every message to filter tools, so it would grow a second, thinner Session model and apply Selectors in two places. Translating 2026-07-28 Callers belongs to the design ADR-0002 sets out for them, for both kinds of Service.
- One Link per Service, shared by its Grants. Rejected for v1: per-Grant request limits and a Grant's end would have to be tracked inside a shared object, and one Grant could affect another. A raw tool list can still be cached per Service later without changing this decision.
- Speak 2026-07-28 to a Service that supports it, or probe for it. Deferred to the design for 2026-07-28 Callers: it adds a second Service-side protocol path, and ADR-0002 speaks the 2025-era protocol to every Child.
- Read Norn's token file format only (`token_file` with `token_label`). Rejected: it builds one tool's file format into a proxy meant to front tools outside the fleet.
- A file that holds only the secret. Rejected as the only form: the operator would copy Norn's secret into a second file, which goes stale when the token rotates.
- Stop the Link on any bad answer, as a Child is stopped for unreadable output. Rejected: a Child's stream cannot be resynchronized after unreadable output, while one bad HTTP answer says nothing about the Service's other requests.
- Stop the Link on a reset or closed connection as well as a refused one. Rejected: Bun reports an ordinary keep-alive race, and one handler failing mid-stream, the same way as a reset, so each would fail every request of the Grant and back off.
- Keep the stored tool list until a notification or a new start. Rejected: under steady use a Link could keep a tool's old hints and Groups indefinitely after the Service is upgraded.
- Fetch the tool list again before every `tools/call`. Rejected in favor of a maximum age: it adds a round trip to every call, while the maximum age bounds the window at a fraction of the cost.
- Allow `localhost` in `url`. Rejected: name resolution can reach an address the Service does not bind.
- Deliver the Grant's Identity in `_meta` on each request. Deferred: Norn needs none, and no Service has designed how it would receive one.

## Consequences

Norn's two checks hold by construction: Modgud sends no `Origin` header and uses no proxy, and it opens with a 2025-11-25 `initialize`, which Norn serves. A Bun `fetch` sends no `Origin` header of its own, and the implementation pins that with a test.
Sessions, limits, renumbering, and Selector enforcement stay one code path for both kinds of Service.
An HTTP Service's tool list changes reach Modgud through a list-change notification on a POST's stream, a new start, or the maximum age. For up to `tool_list_max_age_seconds` after a Service changes a tool's hints or Groups without notifying, Selectors apply the old ones, so an `allow hint:readOnly` or a `deny group:` Selector can let through a call that the new values would refuse. A Child has no such window.
Plain HTTP on loopback authenticates neither side. Any local process that can read the bearer file can call the Service directly, bypassing Modgud's Selectors. Any local account that binds the Service's address while the Service is down receives the bearer at Modgud's next start, and can answer as the Service. An HTTP Service is therefore trusted only as far as every account on the host, which is broader than ADR-0002's trust in the one OS account that runs Modgud and its Children.
Each Grant pays its own `initialize`, and from Phase 2 its own tool list fetches, over loopback. While a Service is down, each Grant backs off on its own.
Bun's `fetch` holds at most 256 requests in flight across the whole process, so the Grants of every HTTP Service share that bound. Once the Grants' requests and Modgud's own POSTs together pass 256, which four Grants at their limit of 64 already reach, requests queue, and an `initialize` that queues past its deadline fails its start.
A Caller that retries after a Link stops may run a tool call twice, because the first call may still finish on the Service.
A tool call that runs longer than the Service's idle timeout without any message in either direction is cut off when the Link stops, as for a Child.
A Service that ends its streams early and expects clients to resume them is not supported.
The behaviors in the Context are Norn's stated contract. Modgud is checked against the real `norn serve` once Norn's `/mcp` exists.
